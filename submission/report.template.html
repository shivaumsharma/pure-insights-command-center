1. Summary

After the move from Tableau Server to a custom portal, the business lost visibility of report usage, refresh failures, report ownership and Snowflake compute cost. I built an admin dashboard with role-based access, alerts that arrive over a WebSocket when a report loads slowly or a refresh fails, and a suite of Snowflake SQL scripts that attribute credits to individual reports and work out the cost per active view. Every headline number was also re-derived by a separate Python program that shares no code with the application, and the two were compared item by item.

2. Execution tasks

Task 1: Full-stack web application with role-based access

  • React front end and an Express API served from one address. Pages: sign-in, overview, reports, report detail, alerts, costs, orphaned reports, data quality.
  • Sign-in returns a signed JWT (HS256, 8 hours). Three roles are enforced in the API, not only hidden in the interface:
RoleCan do
AdminEverything: reconciliation, quarantine ledger, orphaned reports, audit trail, reassigning owners.
OwnerHealth, detail, cost and alerts for the reports they currently own. Anyone else's report returns 404.
ViewerFleet and report health, read-only. No cost data of any kind.
  • Orphaned reports: an admin sees every report with no current owner, ranked by spend, and can assign an owner. Each change is recorded in an audit trail and can be undone. A role/route matrix test and an ownership-scoping test cover every endpoint.

Task 2: Real-time telemetry and WebSocket alerting

  • An alert is raised when a report's load time is over 15 s, or when an automated refresh fails or times out. Severity: over 15 s low, over 25 s medium, over 35 s high, 55 s or more critical. A failed refresh is high, three in a row is critical. A status of UNKNOWN raises nothing and resolves nothing.
  • 74% of readings are over the limit, so a simple threshold would alert on almost everything. Each condition has a lifecycle: TRIGGERED (first time), ESCALATED (worse than last time, sent at once), REPEATED (still true after a 6-hour cooldown), RESOLVED (two clear readings in a row). Held-back repeats are counted on the next alert. Result: 2,026 breaching readings become 838 alerts that need attention.
  • Alerts are pushed over a WebSocket and filtered by role on the server, so an owner never receives another owner's alerts. The server replays the cleaned readings at 10 per second to simulate telemetry.
  • A client that reconnects sends the last alert number and stream id it saw and receives exactly the alerts it missed, once each, then live ones. If events were dropped, or the server restarted, it is told and refetches over REST. Without the stream id, a restart would make every new alert look already seen.
  • Every one of the 1,181 alert events the engine produced was matched against a separate Python implementation of the same rules.

Task 3: Cloud cost allocation engine

  • Snowflake bills per warehouse-hour, not per query. Each hour's credits are therefore split across the queries that ran in it in proportion to their elapsed time, and a report's credits are the sum over its hours. Failed and timed-out queries still hold the warehouse, so they keep their share. Credits are conserved: the shares in an hour add up to that hour's metered credits.
  • Cost per report = attributed credits × credit price + AWS hosting cost. Cost per active user view = that cost divided by total monthly active views (pooled over a report's readings, so one reading with very few views cannot distort it). Spend in readings with zero views is shown separately as idle cost. The data has no price for a Snowflake credit, so I used a round $3 per credit as a rough estimate. Dollar totals are good for comparing reports with each other, not as exact amounts.
  • Eight reconciliation checks (R1 to R8) re-derive and cross-check the numbers from the raw tables. Results are in section 5. The full scripts are in Appendix B.
  • The question's "active user counts versus AWS hosting cost" discrepancy: the fleet's average hosting cost per view is computed, and a reading is flagged when its cost is 3 times above or below what its views predict, or when it has cost but no views. The Costs page plots every reading against that average with the 3x band.

5. Evaluator rubric headings

Full-stack web architecture

  • Four tiers: the React dashboard; the Express backend (REST API with JWT and three roles, alert engine, WebSocket hub); the SQL suite; and the data layer (cleaning pipeline, simulated Snowflake usage logs, exceptions ledger). The raw CSV flows through the cleaning step, which quarantines and never deletes, into the usage logs the SQL reads.
  • One process serves the API, the WebSocket and the built interface, so there is no cross-origin setup. The interface is served with a strict Content-Security-Policy; other origins are refused at the WebSocket handshake.
  • The cost scripts use portable SQL, so the same files run on Snowflake and on a local SQLite stand-in used for fast tests.
  • Every threshold that is my choice rather than the brief's (10% credit tolerance, 3x hosting band, severity tiers, 6-hour cooldown, $3 credit price) is written down with its reason in a decision log of 46 entries.

Real-time alerting and telemetry

  • Alert rules, severity, lifecycle and de-duplication are described in Task 2. The WebSocket protocol, close codes and reconnect rules are in Appendix A.
  • Tested over real sockets (21 tests): authentication in the first message, role filtering, replay after a reconnect, restart detection, limits on connections and message size, and rejection of foreign origins.

7. Additional work, limits and next steps

  • Explanations of alerts, checked against the data. An alert can be explained by a language model or by plain rules. The model is not trusted: it receives a numbered evidence pack and must cite which datapoint supports each claim and the value it read. A checker compares every citation with the real data and rejects numbers that are not in the evidence. Answers that pass are shown with a list of how they were checked; answers that cannot be verified wait for an admin; answers that contradict the data are withheld, and others see the rule-based explanation instead. On 10 alerts, four free local models passed the checks 6, 3, 0 and 0 times, and the rule-based version 9 times. That is a small sample.
  • Data limits. The usage logs are simulated from the CSV, so warehouse totals equal the CSV by construction. The reconciliation matters when run on real ACCOUNT_USAGE data. Dollar amounts rest on a rough credit price (see Task 3).
  • Scope of the checks. The Python validator follows the same written rules as the application, in a different language, so it catches coding slips and drift rather than a different reading of the brief.
  • Next. Run the suite against real ACCOUNT_USAGE views, add a flag-only statistical screen beside the rules, and store alert history so it survives a restart.

Appendix A. REST API and WebSocket specification

Base URL http://localhost:3101. All API routes are under /api, return JSON and use one error shape: { "error": { "code": "FORBIDDEN", "message": "...", "details": {} } }.

StatuscodeMeaning
400BAD_REQUESTInvalid query parameter, body or id
401UNAUTHENTICATED / INVALID_CREDENTIALSNo, bad, expired or forged token; wrong email or password
403FORBIDDENSigned in, but the role may not do this
404NOT_FOUNDUnknown route or report, or a report outside an owner's scope
413PAYLOAD_TOO_LARGEBody over 10 KB
429TOO_MANY_ATTEMPTSFive failed sign-ins for one email and address in 15 minutes (see Retry-After)
500INTERNALGeneric message only; detail is logged on the server

A1. Authentication and roles

POST /api/auth/login with { "email", "password" } returns { token, token_type: "Bearer", expires_in, user }. Send Authorization: Bearer <token> on every other request. Tokens are HS256 JWTs (8 hours) carrying only email and role; the algorithm is pinned on verification. A wrong password and an unknown email return the same 401. GET /api/auth/me returns the signed-in user. GET /healthz is an unauthenticated liveness check.

A3. Alert object

{ "event_id": 42, "alert_type": "LATENCY", "lifecycle": "ESCALATED", "severity": "high",
  "report_id": "RPT_201", "report_name": "Analytics Dashboard 2", "observation_id": "RPT_201:004",
  "observed_at": "2026-09-01T03:00:30.000Z", "suppressed_since_last": 2,
  "value": 41.2, "threshold": 15, "message": "RPT_201 (Analytics Dashboard 2) load time 41.2 s is over 15 s (high)" }

Lifecycle: TRIGGERED, ESCALATED, REPEATED (after the 6-hour cooldown), RESOLVED (two clear readings). Refresh-failure alerts carry the status and consecutive_failures; RESOLVED alerts carry active_for_ms. Times are event time, not wall-clock time. Severity: over 15 s low, over 25 s medium, over 35 s high, 55 s or more critical; a failed refresh is high, three in a row critical.

A4. WebSocket ws://localhost:3101/ws

A browser WebSocket cannot set headers and a token in the URL leaks into logs, so the token is sent in the first message.

client -> { "type": "auth", "token": "<jwt>", "last_event_id": 41, "stream_id": "9f3a1c2e" }   // last two optional
server -> { "type": "ready", "user": {...}, "last_event_id": 57, "stream_id": "9f3a1c2e", "resumed": true }
server -> { "type": "gap", "reason": "dropped" | "restarted", "oldest_event_id": 50, "last_event_id": 57 }   // only if needed
server -> { "type": "alert", "event_id": 42, "alert_type": "LATENCY", ... }       // missed alerts oldest first, then live
client -> { "type": "ping" }      server -> { "type": "pong", "server_time": "..." }
server -> { "type": "error", "code": "...", "message": "..." }                   // then the socket closes
  • Reconnecting. Remember the highest event_id processed and the stream_id from ready. On reconnect send both: you receive exactly the alerts you missed (only those your role may see), in order, each once, then live alerts. If gap arrives, events were dropped from the bounded history (2,000 alerts): refetch GET /api/alerts and GET /api/alerts/active. Reconnect with exponential backoff and jitter. Omit last_event_id on a first connection to get live alerts only.
  • Server restarts. Event ids start again from 1 after a restart, so an id only means something within one run, which is what stream_id names. If the stream_id sent is not current (or last_event_id is beyond the newest event) the server sends gap with reason "restarted" and replays nothing; the client resets to the id in ready and refetches over REST.
  • Close codes. 4401 not authenticated, bad or expired token, 5 s authentication timeout, or token expired while connected. 4429 more than 5 connections for one user. 1008 invalid message or too many bad messages. 1003 binary frame. 1009 message over 4 KB. 1001 server shutting down. The server pings every 30 s and drops clients that do not answer.
  • Handshake. Only /ws. A browser Origin is accepted when it matches the server's own origin or is listed in ALLOWED_ORIGINS; anything else gets 403, including look-alike hosts, other ports and a null origin. Clients that send no Origin (scripts, tests) are allowed because the token authenticates them.
  • Telemetry source. The server replays the cleaned readings at REPLAY_EVENTS_PER_SECOND (default 10) through the alert engine, then loops with timestamps shifted forward.
