  • Authentication. POST /api/auth/login returns a signed JWT (HS256, algorithm pinned, 8 h). Five wrong sign-ins for one email and address in 15 minutes are throttled. Wrong password and unknown email give the same 401.

3. Real-time alerting

An alert is raised when a report's load time is over 15 s, or an automated refresh fails or times out. Alerts are computed by an event-time engine as readings arrive and pushed to every connected client the role may see.

RuleBehaviour
Severity (load time)over 15 s low · over 25 s medium · over 35 s high · 55 s or more critical. A failed or timed-out refresh is high; three in a row is critical. An UNKNOWN status raises nothing and resolves nothing.
LifecycleTRIGGERED (first time) → ESCALATED (worse; sent at once) → REPEATED (still true after a 6 h cooldown) → RESOLVED (two consecutive clear readings).
De-duplication74% of readings breach 15 s, so repeats are held back and counted (suppressed_since_last): 2,026 breaching readings become 838 alerts needing attention.
Telemetry sourceThe cleaned observations are replayed at 10 per second through the engine, then loop with timestamps moved forward. Time in alerts is event time, not wall-clock time.
ReconnectA client sends the last event_id and stream_id it saw and receives exactly the alerts it missed, once each, then live ones. If events were dropped, or the server restarted, it gets a gap message and refetches over REST.

Close codes: 4401 not authenticated, bad or expired token, or 5 s auth timeout · 4429 more than 5 connections for a user · 1008 invalid message · 1003 binary frame · 1009 over 4 KB · 1001 server shutting down. The server pings every 30 s. Browser origins other than the server's own (or ALLOWED_ORIGINS) are refused with 403. Alerts are filtered by role on the server, so an owner never receives another owner's alerts.

5. Cloud cost SQL: attributing credits to reports

Method. Snowflake bills per warehouse-hour, not per query. The standard way to cost queries on a shared warehouse is to split each warehouse-hour's credits across the queries that ran in it, in proportion to their share of elapsed time. A report's credits are the sum over the hours it ran. Failed and timed-out queries still hold the warehouse, so they keep their share. Credits are conserved: the attributed credits in an hour add up to that hour's metered credits.

-- sql/10_credit_attribution.sql (core of it)
SUM(w.elapsed_ms) OVER (PARTITION BY w.warehouse_name, w.window_start)     AS window_elapsed_ms,
CASE WHEN window_elapsed_ms > 0 THEN elapsed_ms * 1.0 / window_elapsed_ms ELSE 0 END AS workload_share,
workload_share * window_credits                                              AS attributed_credits
FROM sim_account_usage.query_history q
JOIN sim_account_usage.warehouse_metering_history m
  ON m.warehouse_name = q.warehouse_name AND q.start_time >= m.start_time AND q.start_time < m.end_time

Statistical anomaly detection was tested and rejected as the method: every numeric column is spread evenly across its range, so the 1.5x IQR and 3-standard-deviation tests flag nothing, and the 24 negative values sit well inside those fences. They are caught by a rule (credits cannot be negative). Thirteen findings in all, each with evidence, impact, who to route it to and a next step, are in docs/validation-findings.md.

7. Quality, and how far to trust the numbers

  • 497 automated tests (240 backend, 257 frontend), each run on a clean machine by GitHub Actions: data-drift check, tests, build, and two end-to-end smoke runs that start the whole product. Tests were mutation-checked: deliberately breaking the code in throwaway copies and confirming a test fails. One mutation (removing a divide-by-zero guard) cannot be detected locally and is recorded as such.
  • Independent validation: npm run validate runs a separate Python program that re-derives every headline number from the raw CSV and compares it item by item with the app: 68 checks, all passing. It also parses the SQL as Snowflake SQL, resolves every column and table against the schema, and confirms the CSV column order matches the tables.

8. Beyond the brief: "Explain this alert", with the AI checked

Because the role is about validating AI output, each alert can be explained by a model (hosted, or a free local one through Ollama) or by plain rules. The model is not trusted: it receives a numbered evidence pack and must cite which fact supports each claim and the value it read. A checker compares every citation with the real data, tests each cause against a data rule, and rejects numbers not in the evidence. Verdicts: passed (shown, with a "how it was checked" list), could not be verified (held for an admin to approve or dismiss), or contradicts the data (withheld). When the AI's answer is held, everyone else sees the rule-based answer for the same alert if it passed the same checks, labelled as rule-based.

Measured, small sample: four free local models on 10 alerts each passed the checks 6 (Llama 3.1 8B), 3 (Gemma 2 9B), 0 (Qwen 2.5 7B) and 0 (Qwen 2.5 1.5B) times; the rule-based control passed 9 of the same 10. This is a small, untuned sample, not a claim about AI in general, and no hosted model was run.

9. Limits, and what I would do next

  • Never run on real Snowflake. The trial had expired. The scripts are portable SQL, tested on SQLite with hand-worked fixtures, re-derived in Python, and checked statically as Snowflake SQL. A step-by-step run guide with expected results is in docs/snowflake-run.md. The parser is lenient, so a pass means "no typos or malformed structure it can see", not "valid on Snowflake".
  • The usage logs are simulated from the CSV, so warehouse totals match it by construction. The reconciliation matters on real ACCOUNT_USAGE data.
  • The CSV has no timestamps. Alert order rests on a synthetic timeline (the k-th row of a report is its k-th hourly reading). The columns are statistically unrelated, so rankings reflect the generator and should not be read as business conclusions.
  • Choices that are mine, not the brief's: the 10% credit tolerance, the 3x hosting band, the severity tiers, the 6 h cooldown, the $3 placeholder price. Each is in the decision log.
  • Next: run the SQL on a real account and compare; add a flag-only statistical screen beside the rules for real data; add a stored history so alerts survive a restart.
